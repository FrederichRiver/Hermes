## 1.4 术语与缩写

### 1.4.1 业务术语

| 术语 | 定义 |
|:---|:---|
| 量化交易 | 利用数学模型和计算机程序进行自动化交易决策和执行的投资方式 |
| 策略 | 一套完整的交易规则，包括信号生成、风控、仓位管理等逻辑 |
| 因子 | 用于解释资产收益或预测未来表现的特征变量，如市盈率、波动率等 |
| 回测 | 使用历史数据验证交易策略表现的过程 |
| 实盘 | 在真实市场环境中使用真实资金进行交易 |
| 模拟交易 | 使用实时市场数据但模拟成交的虚拟交易环境 |
| 夏普比率 | 风险调整后的收益指标，衡量单位风险所获得的超额收益 |
| 最大回撤 | 策略净值从历史高点到低点的最大跌幅 |
| 滑点 | 预期成交价格与实际成交价格之间的差异 |
| 订单簿 | 记录某一证券所有未成交买单和卖单的电子列表 |
| Alpha | 超越市场基准的超额收益能力 |
| Beta | 相对于市场整体波动的系统性风险暴露 |
| MVP | Minimum Viable Product，最小可行产品 |
| 因子 | 用于预测市场走势的特征变量 |

## 简介

### 目的与范围

#### 文档目的

本文档旨在为股票量化交易系统（QTS）提供全面、详细的技术设计规范，具体目标包括：

- **架构蓝图**：定义系统的整体技术架构、模块划分和交互关系，为开发团队提供统一的技术愿景
- **开发指南**：明确各模块的职责边界、接口契约和实现约束，指导编码实现
- **沟通媒介**：作为技术团队、产品团队、业务团队之间的标准化沟通工具
- **验收基准**：定义系统功能和非功能性需求的验收标准
- **演进基础**：记录关键设计决策（ADRs），支持系统的持续演进和知识传承

#### 系统范围

**包含范围（In-Scope）：**

| 领域       | 具体内容                                                         |
| ---------- | --------------------------------------------------------------- |
| 资产类别   | A股股票、ETF、LOF、可转债（初期）；期货、期权（二期）           |
| 市场接入   | 国内证券交易所（上交所、深交所、北交所）；支持Level-2行情       |
| 交易类型   | 现货交易、融资融券、算法交易（TWAP/VWAP等）                     |
| 策略支持   | 股票多因子选股、CTA趋势跟踪、统计套利、事件驱动                 |
| 时间维度   | 日线、分钟线、Tick级策略；支持日内回转交易                      |
| 数据覆盖   | 行情数据、财务数据、alternative data（舆情、供应链等）          |
| 模型支持   | 传统统计模型、机器学习模型、深度学习模型、大语言模型            |

**不包含范围（Out-of-Scope）：**

| 领域         | 说明                       | 备注           |
| ------------ | -------------------------- | -------------- |
| 外汇交易     | 不涉及外汇保证金交易        | 未来可能扩展   |
| 加密货币     | 不涉及数字货币交易          | 监管合规考虑   |
| 境外市场     | 港股、美股暂不支持          | 二期规划       |
| 高频交易     | 延迟要求>10ms的策略         | 需要专用硬件   |
| 完全自主决策 | 所有交易需人工确认或风控审核 | 合规要求       |

### 设计目标

#### 核心设计原则

| 优先级 | 原则           | 说明                                 | 权衡考量                 |
| ------ | -------------- | ------------------------------------ | ------------------------ |
| P0     | 正确性优先     | 交易计算、风控逻辑、资金清算必须100%准确 | 牺牲部分性能换取准确性   |
| P0     | 风险可控       | 多层次风控、熔断机制、人工干预能力       | 增加系统复杂度           |
| P1     | 水平扩展       | 支持从单机到集群的无缝扩展               | 初期引入分布式复杂度     |
| P1     | 低延迟         | 关键路径延迟可控（<100ms）               | 不追求极致高频           |
| P2     | 多租户隔离     | 策略、账户、数据严格隔离                 | 增加资源开销             |
| P2     | 可观测性       | 全链路监控、可追溯、可审计               | 增加存储成本             |

#### 关键设计决策 (Key Design Decisions)

| 决策ID  | 决策内容                   | 决策理由                                   | 影响范围                   |
| ------- | -------------------------- | ------------------------------------------ | -------------------------- |
| ADR-001 | 采用Agent-Based架构        | 支持自治组件、灵活扩展、符合量化领域模型   | 整体架构、通信机制         |
| ADR-002 | Python为主要开发语言       | 量化生态丰富（pandas/numpy）、研究员易上手 | 性能关键路径需优化         |
| ADR-003 | 多数据库混合存储           | 不同数据特性匹配最佳存储方案               | 数据一致性、运维复杂度     |
| ADR-004 | 事件驱动+批处理混合        | 实时交易与离线分析兼顾                     | 系统复杂度、资源调度       |
| ADR-005 | 初期单机部署，预留集群扩展 | 降低初期成本，支持业务增长                 | 架构设计需考虑分布式       |
| ADR-006 | 策略代码与执行引擎分离     | 支持策略热更新、沙箱安全执行               | 策略加载机制、版本管理     |

##### 接口规格概述

**行情数据接口（输入）：**

- 协议：交易所Binary协议 / WebSocket
- 频率：Tick级（逐笔），约10万条/秒/市场
- 内容：订单簿（10档）、成交明细、指数、期权行情
- 处理：系统需具备高并发写入能力，支持数据回放

**交易接口（双向）：**

- 协议：券商SDK（C++封装）/ FIX 4.4
- 延迟： round-trip < 50ms（网络层）
- 功能：报单、撤单、查询、资金划转
- 可靠性：支持订单幂等性，防止重复下单

## 第4章 架构总览（修订版）

### 4.1 架构原则与约束（修订）

#### 4.1.1 核心架构原则（单人开发适配）

| 原则ID   | 原则名称     | 具体定义     | 设计体现      |
|----------|--------------|---------------|--------------|
| AP-001   | 极简优先     | 如无必要，勿增实体。每个组件必须有明确且不可替代的价值 | 拒绝微服务、服务网格等重量级方案           |
| AP-002   | 单机思维     | 设计初期假设单机部署，仅在明确瓶颈处预留扩展点         | 进程内通信替代RPC；SQLite替代分布式数据库  |
| AP-003   | Python原生   | 优先使用Python生态，避免多语言混合带来的心智负担       | 全栈Python，包括性能优化（Numba/Cython）   |
| AP-004   | 文件即接口   | 配置文件、数据文件、日志文件优先使用标准格式（YAML/JSON/Parquet） | 降低调试复杂度，便于手动检查         |
| AP-005   | 显式优于隐式 | 避免魔法和自动化黑盒，流程和状态转换清晰可见           | 显式事件循环；手动资源管理                 |
| AP-006   | 可调试性     | 任何时刻可通过print、日志、文件检查系统状态             | 结构化日志；状态持久化；可重现执行          |

### ADR-003: 事件总线简化（进程内）

- **状态**: 已批准
- **背景**: 单机部署，无需分布式消息队列
- **决策**: 使用Python asyncio Queue实现进程内事件总线

```python
# 简化实现（核心代码<100行）
class EventBus:
    def __init__(self):
        self._subscribers: Dict[str, List[Queue]] = defaultdict(list)
    
    async def publish(self, event_type: str, payload: dict):
        for queue in self._subscribers[event_type]:
            await queue.put(payload)
    
    def subscribe(self, event_type: str) -> Queue:
        queue = Queue()
        self._subscribers[event_type].append(queue)
        return queue
```

- **优势**: 零依赖；调试简单（直接print）；类型安全
- **限制**: 仅单机；重启丢失（需配合持久化）

#### 5.2.2 协程任务调度

```python
# 核心调度逻辑示意（实际实现）
async def main():
    # 初始化事件总线
    event_bus = EventBus()
    
    # 创建Agent实例
    agents = {
        'scheduler': SchedulerAgent(event_bus),
        'data': DataAgent(event_bus),
        'risk': RiskAgent(event_bus),
        'strategy': StrategyAgent(event_bus),
        'execution': ExecutionAgent(event_bus),
        'market': MarketAgent(event_bus),
        'account': AccountAgent(event_bus),
    }
    
    # 启动所有Agent（协程）
    tasks = [
        asyncio.create_task(agent.run())
        for agent in agents.values()
    ]
    
    # 启动FastAPI（主协程）
    config = uvicorn.Config(app, host="0.0.0.0", port=8000)
    server = uvicorn.Server(config)
    tasks.append(asyncio.create_task(server.serve()))
    
    # 优雅关闭处理
    try:
        await asyncio.gather(*tasks)
    except asyncio.CancelledError:
        for agent in agents.values():
            await agent.shutdown()

if __name__ == "__main__":
    asyncio.run(main())
```

### 5.6 扩展性设计

#### 5.6.1 预留扩展点

| 扩展点 | 当前实现 | 未来扩展 | 触发条件 |
|--------|----------|----------|----------|
| 数据库 | SQLite | MySQL/PostgreSQL | 数据量>100GB或需要远程访问 |
| 缓存 | Python dict | Redis Cluster | 多进程部署或分布式缓存需求 |
| 消息队列 | asyncio Queue | Redis Streams/RabbitMQ | 多机部署或需要持久化消息 |
| 计算 | 单进程 | ProcessPool/多机 | CPU瓶颈（因子计算耗时>1分钟） |
| 模型推理 | 本地CPU | GPU/模型服务(Triton) | 模型复杂度提升（大语言模型） |
| 行情接入 | 单源 | 多源聚合 | 需要数据源冗余或跨市场 |
| UI | Web | 移动端/桌面端 | 需要移动监控或专业交易界面 |

# 第8章 接口设计

## 8.1 接口设计原则

### 8.1.1 设计目标

| 目标 | 说明 | 实现方式 |
|:---|:---|:---|
| **简单直观** | 接口命名和结构符合业务直觉，无需额外文档即可猜测用途 | RESTful资源命名；语义化HTTP方法 |

## 8.7 接口安全设计（简化版）

### 8.7.1 认证机制

| 场景 | 机制 | 实现 |
|:---|:---|:---|
| Web界面 | Cookie Session | FastAPI内置session |
| API调用 | Bearer Token | Header: `Authorization: Bearer <token>` |
| WebSocket | URL Token | `ws://host/ws/v1/market?token=<token>` |

**Token管理**：
- 生成：登录时生成JWT或随机字符串
- 有效期：24小时（可配置）
- 刷新：支持自动刷新或重新登录
- 吊销：服务端维护有效token列表（内存或Redis）

## 8.8 接口示例场景

### 8.8.1 完整交易流程接口调用

```
场景：策略生成买入信号，经风控检查，执行订单，成交回报

1. 策略Agent内部生成信号
   （内部事件：strategy.signal.generated）

2. 风控Agent检查（内部事件交互）
   RiskAgent → 发布 risk.check.request
   RiskAgent ← 接收 risk.check.result (passed)

3. 策略Agent提交订单
   POST /api/v1/orders
   Body: {sub_account_id: "sa_001", symbol: "600000.SH", 
          side: "BUY", type: "LIMIT", quantity: 1000, price: 10.50}
   
   Response: {order_id: "ord_202403161430000001", status: "PENDING"}

4. 执行Agent处理（内部事件流）
   - 发布 order.submitted
   - 网关报单成功 → 发布 order.accepted
   - WebSocket推送：{type: "data", channel: "account.order", ...}

5. 交易所成交
   - 网关接收成交回报
   - 发布 order.filled
   - WebSocket推送成交
   - 账户Agent更新持仓资金

6. 客户端查询结果
   GET /api/v1/orders/ord_202403161430000001
   Response: {status: "FILLED", filled_qty: 1000, avg_price: 10.50, 
             trades: [{trade_id: "t_001", price: 10.50, ...}]}
```

   }

| 内存使用 | `free`命令检查 | >90%持续5分钟 | 机器人 |
| 数据库大小 | `ls -lh`检查 | >40GB | 机器人 |
| 交易异常 | 日志关键字监控 | 出现"ERROR"或"REJECT" | 立即机器人通知 |
| 数据源中断 | 心跳超时 | >5分钟无数据 | 机器人 |

**监控脚本示例（health_check.sh）**：
```bash
#!/bin/bash
# 健康检查脚本

HEALTH_URL="http://localhost:8000/health"
WEBHOOK_URL="${DINGTALK_WEBHOOK}"

# 检查服务健康
if ! curl -sf $HEALTH_URL > /dev/null; then
    message="【告警】QTS服务无响应，请检查！"
    curl -s -X POST $WEBHOOK_URL -H "Content-Type: application/json" \
        -d "{\"text\": \"$message\"}"
    exit 1
fi

# 检查磁盘空间
DISK_USAGE=$(df /app/data | awk 'NR==2 {print $5}' | sed 's/%//')
if [ $DISK_USAGE -gt 85 ]; then
    message="【告警】磁盘使用率${DISK_USAGE}%，请及时清理！"
    curl -s -X POST $WEBHOOK_URL -H "Content-Type: application/json" \
        -d "{\"text\": \"$message\"}"
fi

exit 0
```

## 10.5 备份与恢复

### 10.5.1 备份策略

| 数据 | 备份方式 | 频率 | 保留期 | 存储位置 |
|:---|:---|:---:|:---:|:---|
| SQLite数据库 | 热备份（WAL模式）+ 定时复制 | 实时 + 每日 | 30天 | 本地 + 云存储 |
| Parquet文件 | rsync增量同步 | 每日 | 永久 | 云存储 |
| 配置文件 | Git提交 | 每次变更 | 永久 | Git仓库 |
| 策略代码 | Git提交 | 每次变更 | 永久 | Git仓库 |
| 日志文件 | 压缩归档 | 每日轮转 | 7天 | 本地（可删除） |

**备份脚本（backup.sh）**：
```bash
#!/bin/bash
# 日终备份脚本

BACKUP_DIR="/app/backups/$(date +%Y%m%d)"
mkdir -p $BACKUP_DIR

# 1. 备份SQLite（WAL模式支持热备）
sqlite3 /app/data/trading.db ".backup '${BACKUP_DIR}/trading.db'"

# 2. 压缩备份
cd /app/backups && tar czf ${BACKUP_DIR}.tar.gz $(date +%Y%m%d)

# 3. 上传到云存储（使用rclone或ossutil）
rclone copy ${BACKUP_DIR}.tar.gz oss:qts-backups/

# 4. 清理本地旧备份（保留7天）
find /app/backups -name "*.tar.gz" -mtime +7 -delete

# 5. 发送成功通知
curl -s -X POST $DINGTALK_WEBHOOK -H "Content-Type: application/json" \
    -d "{\"text\": \"【备份完成】$(date +%Y-%m-%d) 数据备份成功\"}"
```

### 10.5.2 恢复流程

| 场景 | 步骤 | 预计时间 |
|:---|:---|:---:|
| **单文件恢复** | 1. 停止服务<br>2. 从备份复制文件到data目录<br>3. 启动服务验证 | 10分钟 |
| **完整恢复** | 1. 新服务器部署Docker环境<br>2. 下载最新备份<br>3. 解压到data目录<br>4. 启动服务<br>5. 验证数据完整性 | 30分钟 |
| **时间点恢复** | 1. 恢复基础备份<br>2. 从WAL日志回放（如支持）<br>3. 或接受数据丢失，从Parquet重建 | 1-2小时 |

## 10.6 灾难恢复

### 10.6.1 灾难场景定义

| 级别 | 场景 | 影响 | 恢复目标 |
|:---|:---|:---|:---:|
| **L1-轻微** | 单容器崩溃、网络瞬断 | 服务中断<5分钟 | 5分钟内自动恢复 |
| **L2-中等** | 服务器故障、磁盘损坏 | 数据丢失风险 | 2小时内人工恢复 |
| **L3-严重** | 数据中心故障、账号被封 | 服务完全中断 | 24小时内迁移恢复 |
| **L4-极端** | 代码严重Bug导致资金损失 | 业务终止风险 | 48小时内止损复盘 |

### 10.6.2 应急预案

| 场景 | 检测 | 自动响应 | 人工响应 |
|:---|:---|:---|:---|
| 策略异常交易 | 风控规则触发 | 熔断暂停策略 | 检查日志，确认后恢复或修复 |
| 数据源中断 | 心跳超时 | 切换备用源；降级到缓存数据 | 联系数据供应商；检查网络 |
| 订单异常 | 成交回报异常 | 暂停交易；记录告警 | 核对券商数据；手动修正 |
| 服务器宕机 | 健康检查失败 | 自动重启（如Docker） | 检查服务器状态；必要时迁移 |
| 资金异常 | 对账差异 | 锁定账户；禁止交易 | 逐笔核对；联系券商 |

### 10.6.3 冷备方案

| 组件 | 冷备配置 | 切换时间 |
|:---|:---|:---:|
| 服务器 | 备用云账号，镜像同步 | 30分钟 |
| 数据源 | 2-3家供应商账号 | 即时 |
| 券商通道 | 2家券商接入 | 1小时（需测试） |
| 域名解析 | DNS多记录 | 5分钟 |
